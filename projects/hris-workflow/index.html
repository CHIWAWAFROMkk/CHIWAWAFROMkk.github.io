约 6000 名员工的档案维护，真正的问题不是读出一份 PDF，而是让每一份资料回到正确的员工名下。

我先利用 OpenClaw 调用 DeepSeek 与 GPT API，制作初级版本；再将业务规则整理为面向外企 Microsoft 365 环境的迭代方案。

完成约 3000 名员工的档案补录

面向覆盖约 6000 名员工的 CDP 系统，我结合 AI 辅助提取、Excel 核对与人工复核，累计完成约 3000 名员工的档案补录，补充地址、紧急联系人及教育经历等关键字段，并在离岗前完成该项任务。

工作交付包括补充后的员工信息、缺失与冲突备注，以及按处理结果整理的档案。我的职责贯穿资料下载、范围确认、字段核对、异常处理与结果复查。

我负责什么

员工数据维护

在丹纳赫 HR 派遣实习期间，我参与中国区 CDP 员工信息维护，核对地址、学历、紧急联系人等字段，用 Excel 整理档案与校验数据，并跟进缺失信息及异常记录。

资料需要补充时，对接区域 HR；信息整理后，继续跟进系统更新。按部门筛选工作范围，逐批推进补档。

把重复工作拆成规则

我利用 OpenClaw 调用 DeepSeek 与 GPT API 制作初版，并将档案补录需求拆成主名单、匹配优先级、字段提取、异常分类与审核写回五部分。

在 Excel 辅助处理实践中，我负责设定批次与字段范围、检查输出并纠正执行偏差。企业版进一步把这些经验整理为 Microsoft 365 流程方案。

实际处理中的三次修正

可见员工，不等于本批都要补写

按部门筛选后，仍要区分当前批次已提供资料的人。试处理曾把没有对应 PDF 的可见员工也标成“/”，我指出范围偏差，要求只处理本批资料对应的员工。

由此把“全量查缺”与“本批补写”拆开：全量检查可以登记缺档状态，但不能擅自填入正式字段；补写必须有对应资料和明确范围。

文件名匹配后，还要检查文件内部

历史处理中出现过文件名归属与证件内姓名不一致，也出现过学校名称初读后需要重新核对的情况。这让我把文件内身份核验与证书交叉核对放到写入前，而不是只看文件名。

学历、学校和起止时间要来自同一段明确的教育记录；不能把不同证件的信息拼成一段不存在的经历。

提速先减少重复读取

扫描 PDF 需要逐页查看，Excel 多次定位、读取与保存也带来等待。我提出缩小读取范围，并将同一员工的资料集中处理，减少重复定位和逐页汇报。

企业方案据此增加文件版本缓存与持久化队列；写回仍保留身份确认、审核和回读核对。

保存与归档必须有先后

实践流程使用“未识别”“已识别”“无法识别”整理档案。我将保存成功、回读一致作为完成归档的前提，避免文件已经移走、表格却没有可靠写入。

补充资料到达时回到对应员工处理，不按新文件在目录里的位置顺延写入。

为什么不能只做 PDF 提取？

原来的处理思路从文件夹出发，但文件顺序与 Excel 不一致，部分员工又没有上传档案。即使每份文件都读完，也不能回答“花名册里还有谁没有被处理”。

按文件走：看见已有资料

第 N 个文件不代表第 N 位员工；文件少一份，缺档员工就可能不进入处理范围。输出一个空值，也无法区分“没上传”“没填写”和“看不清”。

按员工走：覆盖整份名单

先固定员工队列，再为每个人查找资料。把档案是否存在、身份是否确认、字段是否可读分别判断，最后按照花名册原序输出。

我如何做取舍

先保证归属，再考虑提取量

姓名可以帮助找文件，但不能独立决定写给谁。同名、工号冲突和多份资料不一致时转人工；宁可保留一个异常，也不把别人的信息补进主表。

把空值拆成可行动的原因

没有档案需要补交资料；档案缺字段需要定向补充；扫描模糊需要重新扫描或人工阅读。状态分类决定下一步找谁、做什么，不只是报表里的标签。

模型输出是候选，不是写入指令

提取结果同时保留来源页码、原文和文件版本。已有内容不覆盖，空白字段经 HR 确认后再写回，避免把识别错误放大成主数据错误。

企业迭代重做数据通道

面向外企环境，关键不只是换一个模型，而是接入获批的数据存储、权限和审核机制。因此企业方案采用 Microsoft 365 组件，并将识别、审核与写回分离。

Microsoft 365

保留 Excel 主名单，以 SharePoint 承接队列与审核；由 Power Automate 调度匹配、提取和写回。

四条流程，各司其职。

建立任务

读取花名册 → 固定原始序号 → 校验唯一工号 → 按员工建立持久化队列。

入口：手动启动一个批次。每个员工只有一个对应任务。

匹配与提取

按队列序号取员工 → 文件名工号 → 文件名姓名 → 文本 / OCR → 身份确认 → 生成字段候选。

缓存按文件版本复用，文件列表不创建员工任务。

审核与写回

HR 逐项确认 → 重读主数据 → 比较旧值 → 仅写空白 → 回读核对 → 登记写入凭据。

一条写入通道；未批准的候选不进入正式花名册。

汇总与续跑

恢复中断任务 → 输出异常、无档案与已完成清单 → 按原始序号合并结果。

业务状态与系统错误分开，失败不会伪装成没有档案。

四种结果，不再混淆。

档案状态判断依据处理结果
未找到电子档案已完成查找，且不存在尚未排除的身份候选进入无档案名单，不用“/”代替状态
档案存在-信息缺失身份确认、内容可读，资料未提供所需字段记录具体缺失字段，其他候选仍可审核
档案存在-识别失败档案归属已确认，相关内容模糊或无法读取标明页码与识别问题，转人工处理
已完成必需字段有依据，审核及写回核对均完成记录来源、审核人与更新时间

同名、重复工号、多份冲突或未知归属文件使用“处理状态：人工审核”，不强行归入无档案。混合问题保留全部原因，识别失败优先于信息缺失。

Power Automate 配置步骤

01 · 主名单与队列
  1. 在受控 SharePoint 文档库保存花名册和档案，启用版本历史。将花名册设为 Excel 表 tblEmployees。
  2. 保留九项补录字段和工号、姓名。增加 EmployeeKey（文本工号）、RowOrder（原始序号）、BatchId，以及档案状态、处理状态、缺失字段、异常备注、文件名称、更新时间。
  3. 使用 Excel Online (Business) 的 List rows present in a table，开启分页，阈值覆盖全量员工；用批次快照固定顺序和人员范围。
  4. 按 RowOrder 升序创建 SharePoint WorkQueue。TaskKey = BatchId + EmployeeKey，启用唯一值；空工号、重复工号先转异常。
  5. 队列建立后才整理文件查找索引。目录枚举、分页与 OCR 归属索引均只用于检索，不产生新员工任务。
02 · 匹配与字段提取
  1. 定时流按序提取 Pending / Retry 任务。首版采用单任务处理；领取任务时记录 LeaseUntil、Attempt 和运行编号。
  2. SharePoint Get files (properties only) 取得候选元数据；按完整工号标记匹配，避免把 123456 匹配到 91234567。姓名精确匹配仅用于缩小候选集。
  3. 对未匹配文件建立内容索引：Get file content → 企业批准的 AI Builder 文本识别；同一 UniqueId + 文件版本只识别一次。姓名不能单独证明身份。
  4. 核对工号、姓名与档案归属。缺少任一身份依据或多个文件冲突时，停止自动补录并转人工。
  5. 读取九个字段，候选结果携带原文片段、页码、文件版本与提取规则版本；文字识别与结构化字段解析分成两步。
  6. 将候选写入 ReviewQueue。无依据返回空值；待审核展示可用“/”，不推测地址、电话、学历或日期。
03 · 人工审核与正式写回
  1. HR 在受限 ReviewQueue 查看原值、候选值和证据，逐字段选择确认、拒绝或修正，并记录审核人和时间。
  2. 只允许审核角色产生批准记录；提取流程不具有批准权限。可用 Approvals 发送任务链接，不在通知中放员工敏感字段。
  3. 独立写回流按序获取批准记录，重新核对工号、姓名、文件版本和原值。已有非空值保持不变；新旧冲突退回审核。
  4. 通过 Excel Online (Business) 按唯一 EmployeeKey 更新明确批准的空白单元格。更新前备份版本，写入后回读核对。
  5. 用 WriteKey = TaskKey + 审核版本记录提交凭据。若超时，先回读判断是否已经写入，再决定重试，避免重复操作。
  6. 写回窗口内关闭其他自动写入并协调人工编辑；Excel 不提供本流程所需的跨客户端原子比较写入，有并发编辑风险时暂停。
04 · 异常汇总与断点续跑
  1. Scope 分为 Try、Catch、Finally，通过 Configure run after 区分失败、超时与成功。
  2. 429 与临时 5xx 使用有上限的指数退避，遵循服务端重试提示；权限错误和文件损坏直接转异常，不循环重试。
  3. 任务保存检查点：候选定位、身份确认、提取完成、审核完成、写入完成。租约过期后可恢复，但先核对写入凭据。
  4. 已完成且文件版本、规则版本均未变化的任务跳过；补传档案或字段来源变化时创建新处理版本，不删除旧日志。
  5. 按 BatchId 筛选任务，按 RowOrder 排序生成汇总工作簿、无档案名单和异常名单。与原快照核对总行数及工号顺序。

表结构与连接器

Excel 主表

工号、姓名、通讯地址、户籍地址、紧急联系人姓名 / 电话 / 关系、最高学历、学位、教育开始 / 结束时间。

工号与电话使用文本，保留前导零；教育时间保留来源精度，不把年月扩写为虚构日期。

结果列：档案状态、处理状态、缺失字段、异常备注、文件名称、更新时间。控制列：EmployeeKey、RowOrder、BatchId。

SharePoint 数据层

WorkQueue：TaskKey、BatchId、RowOrder、EmployeeKey、Name、Stage、Attempt、LeaseUntil。

ReviewQueue：员工、文件版本、字段、原值、候选值、证据位置、缺失字段、异常原因、处理建议、审核状态与审核人。

FileIndex / AuditLog：文件标识与归属线索；阶段事件、错误码、写入凭据及受控版本链接。

索引 BatchId、Stage、EmployeeKey；避免全列表扫描和一次读取大对象。

面向外企的
部署边界

替换数据通道，而非只替换模型

企业版通过租户批准的连接器和识别服务处理档案，不直接沿用初版的外部 DeepSeek / GPT API 调用路径。连接器策略、服务区域、数据保留、许可与 AI 容量由企业管理员核定。

最小权限与可追踪审核

档案读取、字段审核与写回权限分离。对包含原文的动作启用安全输入 / 输出，审计日志保存任务和版本引用；通知与公开作品集不携带真实档案。

顺序、吞吐与恢复

Excel 写回保持串行，识别缓存降低重复调用。正式批量前用小样本测量每页识别耗时、每员工动作数、节流和人工审核时间，据此决定批次规模。

回滚按单元格进行

保存批准前后的值与版本。回滚时仅恢复本批次写过、且当前仍等于写入值的单元格；后续人工修改不被整表备份覆盖。

验收用例

验收对象是正确归属、保留原值、审核门禁和可恢复性。
